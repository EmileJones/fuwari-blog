# 代码的坏味道

## Duplicated Code

如果你在一个以上的地方上看到相同的程序结构，那么可以肯定：设法将他们合二为一，程序会变得更好。

例如下面两种典型情况：

1.  同一个类的两个函数有相同的表达式。

2.  两个互为兄弟的子类内含有相同的表达式。

## Long Method

短函数可以带来很多好处：解释能力、共享能力、选择能力。

现在互联网上对于一个函数应该多长，有很多不同的观点，我个人结合我的经验，赞同的观点是一屏幕原则，即一个函数的长度应该在一个屏幕内。

## Large Class

如果单个类做了太多的事情，其内部往往就会出现很多实例变量，这样还会导致 Duplicated Code。单个类内如果有太多的代码，也就是代码重复、混乱并最终走向死亡的源头。

## Long Parameter List

太长的参数列表难以理解，太多参数会导致前后不一致、不易使用，而且一旦你需要更多的数据，你就不得不修改它。

## Divergent Change

我们希望软件易于更改，一旦更改，我们希望能够跳到代码的某一点，只在此处修改。如果某个Class经常因为不同的原因在不同的方向上发生变化，Divergent Change就出现了。

例如，当你看着一个类说："emm，如果新加入一个数据库，我必须修改这三个函数，如果新加入一个工具我需要修改这四个函数"，那么此时这个类或许拆分成两个更好。

## Shotgun Surgery（散弹式修改）

和Divergent Change正好相反，如果每遇到某种变化，你都必须在许多不同的Class内做出许多小的修改，你所面临的坏味道就是Shotgun Surgery。

## Feature Envy（依恋情结）

函数对某个Class的兴趣高过对自己所处的Class的兴趣，就是Feature Envy。

## Data Clumps

你常常可以看到在很多地方出现相同的三四项数据，这些重复绑在一起出现的数据应该有他们自己的Class。

## Primitive Obsession（基本类型偏执）

面向对象技术的新手通常不愿意在小任务上运用小对象。例如，像是结合数值和币种的Money类等。他们执著于基本数据类型，但是相对于构建小对象代替基本类型的性能牺牲而言，小对象对于代码的可读性和可维护性提升的程度更重要。

## Switch Statements

大多数时候，一看到switch语句，你就应该考虑替换他。

## Parallel Inheritance Hierarchies（平行继承体系）

这是Shotgun Surgery的特殊情况：每当你为某一个类增加子类，必须也为另一个平行的类添加相应的子类。

## Lazy Class

在项目中经常遇到这种情况：某个类原本对得起自己的价值，但是在重构中它身形说说，不再做那么多的工作；或者开发前规划了一些变化，并且添加了一个类来应付这个变化，但是变化并没有发生。不论以上那种情况，请让这个类庄严赴义吧。

## Speculative Generality（频繁的猜测未来）

当有人说"我想我们总有一天要做这个事"，并因而企图以各式各样的钩子和特殊情况来处理一些非必要的事情，Speculative Generality的坏味道就出现了。

## Temporary Field

有时你会看到这样的对象：其内某个实例变量仅为了某种特定情况而设置。这样的代码容易让人不理解，因为你通常认为对象在所有的时候都需要它所有的变量。

## Message Chains

当你看到一个对象请求另一个对象，然后再向后者请求另一个对象，然后再请求另一个对象\...\...这就是Message Chains。

``` java
// 获取客户信用卡的最后4位
String lastFourDigits = customer.getOrder()
                               .getPayment()
                               .getCreditCard()
                               .getLastFourDigits();
```

但并不是所有的Message Chains都是坏东西，例如在Stream的链式调用或者创建一个不可变对象的时候也用到了Message Chains。

## Middle Man

有些人会过度使用委托。某个Class有一半的函数全部都委托给了其他类，这样就是过度运用。

## Inappropriate Intimacy

有时你会看到两个Class过分的亲昵，花费太多的时间去探究彼此的private成分。遇到这样的情况你就应该帮它们划清界限。

## Alternative Classes with Different Interfaces

两个函数做同一件事但却有着不同的签名。请根据它们的用途重新命名。

## Incomplete Library Class

指第三方库或框架提供的类无法完全满足需求，导致开发者不得不通过修改或绕过库类来实现功能。

## Data Class

一个数据类，他的get和set方法只是单纯的获取或者设置这个类的实例字端，这样的类一定过多的被外部的类过分频繁的操控者。

例如：

``` java
// 典型的数据类例子
public class User {
    private String name;
    private String email;
    private int age;

    // 只有getter/setter，没有业务逻辑
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }

    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }

    public int getAge() { return age; }
    public void setAge(int age) { this.age = age; }
}
```

你应该尝试把一些调用行为迁移到Data Class内。

例如：

``` java
public class User {
    private String name;
    private String email;
    private int age;

    // 保留getter，但考虑移除setter或使其更安全
    public String getName() { return name; }
    public String getEmail() { return email; }
    public int getAge() { return age; }

    // 将业务逻辑移到类内部
    public boolean isAdult() {
        return this.age >= 18;
    }

    public boolean isValid() {
        return this.age > 0 &&
               this.email != null &&
               this.email.contains("@") &&
               this.name != null &&
               !this.name.trim().isEmpty();
    }

    // 使用更安全的方法来更新状态
    public void updateEmail(String newEmail) {
        if (isValidEmail(newEmail)) {
            this.email = newEmail;
        } else {
            throw new IllegalArgumentException("Invalid email");
        }
    }

    private boolean isValidEmail(String email) {
        return email != null && email.contains("@");
    }
}
```

## Refused Bequest

之类应该继承超类的函数和数据。但如果它们只从所得到的礼物中，挑选出几样来玩，就是Refused Bequest。

如果子类复用了超类的行为，却又不愿意支持超类的借口，Refused Bequest的坏味道就会变得浓烈。拒绝继承超类的实现，这点我们一点不介意，但是如果拒绝继承超类的接口，那这样导致继承体系被修改，这样也违反了里氏替换原则（LSP）。

## Comments

并不是不应该写注释，注释并不是一种坏味道，它甚至是一种香味。之所以要提到Comments，是因为很多人把注释当作除臭剂来使用，当你看到一段代码有长长的注释，然后发现，这些注释之所以存在是因为代码很糟糕。过多的注释意味着代码很糟糕，好的代码是不需要过多的注释的。

# 代码重构方法

## Extract Method

如果每个函数的粒度都很小，那么函数被复用的机会就会更大；其次，这会使高层函数读起来就像是一系列注释；再次，如果函数都是细粒度，那么函数复写也会更容易些。

``` java
// original code
void printOwing(double amount){
    printBanner();

    // print details
    System.out.println(“name:” + _name);
    System.out.println(“amount:” + amount);
}
```

``` java
// refactored code
void printOwing(double amount){
    printBanner();
    printDetails(amount);
}

void printDetails(double amount){
    System.out.println(“name:” + _name);
    System.out.println(“amount:” + amount);
}
```

## Replace Temp with Query

临时变量的问题时，他们是暂时的，而且只能在所属函数中使用。由于自在所属函数内可见，所以他们会驱使你写出更长的函数，只有这样才能访问到所需的临时变量。

基本不用担心性能问题，而且十有八九也不会出现性能问题，如果有性能问题也可以在优化时期解决。

``` java
// original code

public class Order {

    private int quantity;
    private double itemPrice;

    public Order(int quantity, double itemPrice) {
        this.quantity = quantity;
        this.itemPrice = itemPrice
    }

    public double calculateTotal() {

        double basePrice = quantity * itemPrice; // 临时变量
        double discount;

        if (basePrice > 1000) {
            discount = basePrice * 0.1; // 10% 折扣
        } else {
            discount = basePrice * 0.05; // 5% 折扣
        }

        double tax = basePrice * 0.08; // 8% 税
        double shipping = basePrice > 500 ? 0 : 15; // 运费
        return basePrice - discount + tax + shipping;
    }

}
```

``` java
// refactored code
public class Order {

    private int quantity;
    private double itemPrice;

    public Order(int quantity, double itemPrice) {
        this.quantity = quantity;
        this.itemPrice = itemPrice;
    }

    public double calculateTotal() {
        return basePrice() - discount() + tax() + shipping();
    }

    private double basePrice() {
        return quantity * itemPrice;
    }

    private double discount() {
        if (basePrice() > 1000) {
            return basePrice() * 0.1; // 10% 折扣
        }
        return basePrice() * 0.05; // 5% 折扣
    }

    private double tax() {
        return basePrice() * 0.08; // 8% 税
    }

    private double shipping() {
        return basePrice() > 500 ? 0 : 15; // 运费
    }
}
```

## Introduce Explaining Variable

将复杂的表达式（或者其中一部分）的结果放进一个临时变量，以此变量名称来解释表达式的用途

``` java
// original code
public class UserValidator {

    private User user;

    public boolean isValid() {
        // 复杂的布尔表达式
        return user != null &&
               user.getAge() >= 18 &&
               user.getAge() <= 120 &&
               user.getEmail() != null &&
               user.getEmail().contains("@") &&
               !user.getEmail().endsWith("@test.com") &&
               (user.getPhone() != null || user.getSecondaryPhone() != null);
    }
}
```

``` java
// refactored code
public class UserValidator {

    private User user;

    public boolean isValid() {
        // 验证用户存在
        if (user == null) {
            return false;
        }

        // 解释性变量使逻辑清晰
        boolean isAgeValid = isAdultAge(user.getAge());
        boolean hasValidEmail = isValidEmail(user.getEmail());
        boolean hasContactInfo = hasContactMethod();

        return isAgeValid && hasValidEmail && hasContactInfo;
    }

    // 进一步提取方法（可选）
    private boolean isAdultAge(int age) {
        return age >= 18 && age <= 120;
    }

    private boolean isValidEmail(String email) {
        return email != null &&
               email.contains("@") &&
               !email.endsWith("@test.com");
    }

    private boolean hasContactMethod() {
        return user.getPhone() != null ||
               user.getSecondaryPhone() != null;
    }
}
```

## Split Temporary Variable

使用多个临时变量，每个临时变量只承担一个职责。

``` java
// original code
public class PhysicsCalculator {
    public double calculatePosition(double initialVelocity, double acceleration, double time) {
        double temp = initialVelocity; // 第一次赋值：初始速度

        // 计算中间速度
        temp = temp + acceleration * time; // 第二次赋值：中间速度

        // 计算位移
        temp = initialVelocity  time + 0.5  acceleration  time  time; // 第三次赋值：位移

        return temp; // 返回位移
    }
}
```

``` java
// refactored code
public class PhysicsCalculator {
    public double calculatePosition(double initialVelocity, double acceleration, double time) {
        // 保留初始速度参数
        final double initialVel = initialVelocity;

        // 计算中间速度（v = u + at）
        final double intermediateVelocity = initialVel + acceleration * time;

        // 计算位移（s = ut + 0.5at²）
        final double displacement = initialVel  time + 0.5  acceleration  time  time;

        return displacement;
    }
}
```

## Remove Assignments to Parameters

移除所有对参数进行赋值的语句，使用临时变量接收。

## Replace Method with Method Object

你有一个大函数，使你无法使用Extract Method，那么就将这个函数装入到一个单独的对象中，如此一来局部变量就变成了对象内的字段。

## Substitute Algorithm

如果你发现做一件事可以有更清晰的方式，就应该以较清晰的方式取代复杂的方式。

``` java
// original code
String findCandidate(String[] people) {
    for (int i = 0; i < people.length; i++) {
        if ("Don".equals(people[i])) {
            return "Don";
        }
        if ("John".equals(people[i])) {
            return "John";
        }
        if ("Kent".equals(people[i])) {
            return "Kent";
        }
    }
    return "";
}
```

``` java
// refactored code
String findCandidate(String[] people) {
    List<String> candidates = Arrays.asList("Don", "John", "Kent");
    for (String name : people) {
        if (candidates.contains(name)) {
            return name;
        }
    }
    return "";
}
```

## Move Method

如果一个类有太多行为，或如果一个类与另一个类有太多合作而形成的高度耦合，我就会Move Method。

## Move Field

如果我发现，对于一个字段，在其所驻类之外的另一个类中有过多的函数使用了它，我就会考虑迁移这个字段。

## Extract Class

当一个类承担了过多的职责，以至于其 fields 和 methods 组合变得非常复杂、难以理解，并且这些职责其实可以拆分成两个（或多个）更专一的类。

## Inline Class

Inline Class 和 Extract Class 相反。如果一个类不再承担足够多的责任、不再拥有单独存在的理由，我们就会挑选这个"萎缩类"最平凡的用户，以 Inline Class 的手法将"萎缩类"塞进另一个类中。

## Hide Delegate

当一个客户端对象（Client）通过一个服务器对象（Server）获取到另一个对象（Delegate），然后调用这个 Delegate 的方法。也就是调用链像 `client.getServer().getDelegate().someMethod()`。在这里：Server 对象向外暴露了 Delegate 对象给客户端，客户端绕过 Server 直接操作 Delegate。

``` java
// original code
class Department {
    private Manager manager;
    public Department(Manager m) { manager = m; }
    public Manager getManager() { return manager; }
}

class Person {
    private Department department;
    public Person(Department d) { department = d; }
    public Department getDepartment() { return department; }
}

class Main {
    public static void main(String[] args){
        Person p = new Person(new Department(new Manager("Alice")));
        Manager m = p.getDepartment().getManager();
        System.out.println(m.getName());
    }
}
```

``` java
// refactored code
class Department {
    private Manager manager;
    public Department(Manager m) { manager = m; }
    public Manager getManager() { return manager; }
}

class Person {
    private Department department;
    public Person(Department d) { department = d; }
    // Hide department
    public Manager getManager() {
        return department.getManager();
    }
}

class Main {
    public static void main(String[] args){
        Person p = new Person(new Department(new Manager("Alice")));
        Manager m = p.getManager();
        System.out.println(m.getName());
    }
}
```

## Remove Middle Man

当一个类使用 Hide Delegate 太多次，直到几乎只是将方法调用委托给另一个类，且自己并不增加实质行为时，这个类就是一个 Middle Man 的气味。

解决方法是：把这些委托方法删除，让客户端 直接调用目标类（Delegate）的方法。

``` java
// original code
class Engine {
    void start() { System.out.println("Engine started."); }
}

class Car {
    private Engine engine;
    Car(Engine engine) { this.engine = engine; }
    void startEngine() { engine.start(); }
}

class Client {
    public static void main(String[] args) {
        Engine e = new Engine();
        Car car = new Car(e);
        car.startEngine();
    }
}
```

``` java
// refactored code
class Engine {
    void start() { System.out.println("Engine started."); }
}

class Car {
    private Engine engine;
    Car(Engine engine) { this.engine = engine; }
    Engine getEngine() { return engine; }
}

class Client {
    public static void main(String[] args) {
        Engine e = new Engine();
        Car car = new Car(e);
        car.getEngine().start();
    }
}
```

## Introduce Foreign Method

在用一个已有类或第三方库类（我们称之为 "服务器类"），它缺少某个你自己需要的方法，而你 **无法修改** 那个类（可能因为是第三方库或不方便改动）。那么你应该在你的 "客户端类" 中新建一个方法，这个方法第一个参数就是那个服务器类的实例。然后把你需要的逻辑放在这里。也就是说，你把 "缺失的方法"作为一个 "外部方法（Foreign Method）" 放在客户端里。

但是不要忘记：Introduce Foreign Method 终归是权宜之计。如果有可能，你仍应该将这些函数迁移到他们的理想家园。如果由于代码所有权的原因使你无法迁移，就应该使用 Introduce Local Extension 的重构方法。

``` java
// original code
import java.util.Date;

public class Report {
    private Date previousEnd;

    public Report(Date previousEnd) {
        this.previousEnd = previousEnd;
    }

    public void sendReport() {
        // We want to get the next day, but the Date class doesn’t have a nextDay method.
        Date nextDay = new Date(
            previousEnd.getYear(),
            previousEnd.getMonth(),
            previousEnd.getDate() + 1
        );
        // Other
    }
}
```

``` java
// refactored code
import java.util.Date;

public class Report {
    private Date previousEnd;

    public Report(Date previousEnd) {
        this.previousEnd = previousEnd;
    }

    public void sendReport() {
        Date nextDay = nextDay(previousEnd);  // 用我们自己的方法
        // Other
    }

    private static Date nextDay(Date date) {
        return new Date(
            date.getYear(),
            date.getMonth(),
            date.getDate() + 1
        );
    }
}
```

## Introduce Local Extension

如果你可以修改源代码，最好的方式就是直接加入自己需要的函数。很遗憾，类的作者无法预知未来，他们没能为你预先准备一些有用的函数并且你也无法修改他。

如果只需要一两个函数，你完全可以使用 Introduce Foreign Method 去重构，但是如果需要很多函数，你就可以使用继承（subclassing）或者装饰器（wrapping），我们称这些为 Local Extension。

# 数据重构方式

## Replace Data Value with Object

开发初期，你往往决定以简单的数据项去表示简单的情况。但是随着开发的进行，你可能会发现，这些简单数据项不再那么简单了。

``` java
// original code
public class Order {
    private String customerName;

    public Order(String customerName) {
        this.customerName = customerName;
    }

    public String getCustomerName() {
        return customerName;
    }
}
```

``` java
public class Customer {
    private String name;
    private String id;
    private boolean vip;

    public Customer(String name, String id, boolean vip) {
        this.name = name;
        this.id   = id;
        this.vip  = vip;
    }

    public String getName()   { return name; }
    public String getId()     { return id; }
    public boolean isVip()    { return vip; }

    public double getDiscountRate() {
        return vip ? 0.1 : 0.0;
    }

    private Customer customer;

        return customer.getDiscountRate();
    }
}
```

## Change Value to Reference OR Change Reference to Value

在许多系统中，你都可以对对象做一个有用的分类：引用对象和值对象。

用例子的方式去理解：

- 值对象：例如Date对象，系统中有成百上千个2002/10/27的Date对象，但是他们是否相等完全由其中的数据值去判断，所以你需要重写 `equals()` 和 `hashcode()` 方法。

- 引用对象：例如Person对象，这个世界上每一个人都可以是一个Person对象，甚至可以有两个完全同名、同年龄、同性别的人，像这样的对象，你可以直接使用 `==` 来判断是否相等。

**Change Reference to Value 解决方案：**

假设我们要将C从引用对象变为值对象，如果你只是简单的重写了C类的 `equals()` 和 `hashcode()` 方法，如果在A对象和B对象中同时创建了一个数据完全相同的C对象，那么你可以判断A和B创建的C是一个C，但是如果你在A中修改了C，但是B中的C并不会改变，当再次判断的时候，A中的C和B中的C就不是一个C了，但其实他们在全局角度看，应该是一个C。

为了解决这个问题，就可以使用工厂模式去创建C。

``` java
public class Currency {
    private String code;
    private Currency(String code) {
        this.code = code;
    }
    public String getCode() {
        return code;
    }

    private static final Map<String, Currency> CACHE = new HashMap<>();

    public static Currency of(String code) {
        return CACHE.computeIfAbsent(code, c -> new Currency(c));
    }
}

public class Order {
    private Currency currency;
```

## Replace Array With Object

数组应该只用于"以某种顺序容纳一组相似对象"，有时候你会发现，一个数组容纳了多种不同的对象，则会给用户带来麻烦，因为他们很难记住"数组的第一个元素是人名"这样的约定。

``` java
// original code
String[] row = new String[3];
row[0] = "Liverpool";
row[1] = "15";
```

``` java
// refactored code
Performance row = new Performance();
row.setName("Liverpool");
row.setWins("15);
```

## Change Unidirectional Association to Bidirectional

开发初期，你可能会在两个类之间建立一条单向连接，使其中一个类可以引用另一个类。随着时间推移，你可能会发现被引用的类需要得到其引用的类以便进行某些操作。这时候你就需要将这两个类从"单向关联"改为"双向关联"。

## Change Bidirectional Association to Unidirectional

双向关联很有用，但你也必须为他付出代价，那就是维护双向连接、确保对象被正确创建和删除的复杂度增加。大量的双向连接也很容易造成"将是对象"：某个对象本来已经该死亡了，却仍然保留在系统中，因为他的引用并没有被完全消除。这时候你就需要将这两个类从"双向关联"改为"单向关联"。

## Replace Magic Number with Symbolic Constant

magic number 指的是具有特殊意义，但是又不能明确表示出这种意义的数字。许多语言都允许你声明常量，常量不会造成任何性能开销，但是却可以大大提高代码的可读性。

``` java
// original code
double potentialEnergy(double mass, double height){
    return mass * 9.81 * height;
}
```

``` java
// refactored code
double potentialEnergy(double mass, double height){
    return mass * GRAVITATIONAL_CONSTANT * height;
}
static final double GRAVITATIONAL_CONSTANT = 9.81;
```

## Encapsulate Collection

我们常常会在一个类中使用集合去保存一组实例。这样的类通常也会提供针对该集合的get/set函数。

但是集合不应该完全暴露给用户，让用户去操作这个集合，应该提供一个只读的副本，并且提供自己的添加和删除函数，这样可以控制用户的行为，保证代码安全。
